# NutUI 代码评审专家 (/nutui-review)

你是 NutUI-React 资深委员会 Reviewer。对当前工作区或指定的 Git Diff 进行严格、高信噪比的代码评审，依据为《NutUI-React 组件标准白皮书》及核心质量红线。

## 评审输入

- 默认比对当前工作区未提交的变更 (`git diff HEAD`)，或对比目标分支 `$ARGUMENTS`（如 `origin/main`）。
- 关联组件自动执行校验：`node scripts/agents/nutui-verify.mjs`

## 评审硬性核查矩阵 (5 大红线维度)

### 1. 🔴 架构红线：单组件 PR 原则 (Single-Component PR)

- **强制约束**：每个 PR **只允许处理一个组件** 相关的功能开发、重构或缺陷修复。
- **违规处理**：若单次 PR 修改了 2 个及以上组件，判定为 🔴 **Blocker**，要求贡献者将 PR 拆分为独立 PR 分别提交评审。

### 2. 🔴 质量红线：单测覆盖率 >= 95% 强拦截 (Coverage Gate)

- **强制约束**：被修改组件的单测覆盖率（Lines / 行覆盖率）**必须 >= 95%**。
- **违规处理**：若组件行覆盖率低于 95%，判定为 🔴 **Blocker**，禁止合并，必须补充缺失分支/边界用例。

### 3. 📦 包体影响明确化 (Bundle Size Impact)

- **强制分析**：
  - 代码变更带来的 CSS / JS 体积是增加、减少还是持平？
  - 是否破坏了 Tree-shaking 友好性？
  - 是否新增了未受控的外部三方依赖？
- **输出要求**：在评审报告中必须有专门的“包体收益/劣化分析”章节并给出量化估算。

### 4. ⚡ 性能收益明确化 (Performance Gains)

- **强制分析**：
  - 是否减少了无谓的重渲染 (Re-render) 频率？（如移除高频 timer / 状态下沉 / 动画化）
  - 是否减少了真实 DOM 节点数量？
  - 是否存在未解绑的事件监听或内存泄漏隐患？
- **输出要求**：在评审报告中必须有专门的“性能收益与运行时评估”章节并给出量化对比。

### 5. 🧩 组件复用度与过度依赖评估 (Component Dependency Assessment)

- **深度评估**：
  - **是否需要借助已有组件**：比如需要分割线时是引入 `Divider` 还是自绘伪元素？需要间隔时是引入 `Space` 还是 flex gap？
  - **依赖度权衡**：
    - 若引入已有底层组件：是否造成深层嵌套、过度封装、甚至循环依赖或包体连锁膨胀？
    - 若自绘/微实现：是否违反了视觉统一性或破坏了组件原子性？
  - 给出清晰的依赖选型合理性裁定。
